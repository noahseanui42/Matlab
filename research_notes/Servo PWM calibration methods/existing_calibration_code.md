# Existing Open-Source Code/Projects for Servo PWM↔Angle Calibration (incl. Delta Robots)

## Key Question 1: What open-source delta robot firmware includes calibration routines, and how do they work (even if for steppers)?

### Takeaway
Delta 3D-printer firmwares (Marlin, RepRapFirmware/Duet, Klipper) all implement mature, well-documented geometric self-calibration routines — probing multiple points across the workspace and fitting/adjusting endstop offsets, delta radius, diagonal-rod (arm) length, and per-tower angular/radial position error. These are stepper+probe systems, not servo-angle calibration, but the *calibration philosophy* (parameterize the physical geometry, collect (measured-position, commanded-position) pairs, then least-squares/iteratively solve for the correction parameters) is a directly transferable model for calibrating a servo-driven delta robot's arm-angle-to-effector-position relationship.

### Cited Findings
- **Marlin G33 "Delta Auto Calibration"**: probes a circular grid of points and can calibrate delta height, endstop offsets, delta radius, and per-tower angle/position error; supports a dry-run mode (`V0`); iterates until convergence, computing standard deviation each iteration; results are persisted with `M500`. — [Marlin G33 docs](https://marlinfw.org/docs/gcode/G033.html)
- Marlin's delta geometry (rod length, radius, tower angle offsets) is configured/adjusted via `M665`, where X/Y/Z parameters are the angular offset of each tower from the ideal 120°-spaced position, measured anticlockwise from above. — [Marlin M665 docs](https://marlinfw.org/docs/gcode/M665.html)
- Community forks such as **RichCattell/Marlin** ("Marlin Delta firmware with autocalibration updates"), **T3P3/Marlin-1**, and **MD3DDelta/Marlin-1** exist specifically to add/backport delta auto-calibration to older Marlin versions — reusable as reference implementations of the calibration math even outside their original printer context. — [RichCattell/Marlin](https://github.com/RichCattell/Marlin), [T3P3/Marlin-1](https://github.com/T3P3/Marlin-1), [MD3DDelta/Marlin-1](https://github.com/MD3DDelta/Marlin-1)
- **RepRapFirmware (dc42/Duet3D)** supports a family of calibration models of increasing complexity: 3-factor (endstop corrections only), 4-factor (+ delta radius), 6-factor (+ X/Y tower position corrections), 8-factor (+ tower tilt angles) — i.e., calibration is explicitly modeled as solving for an increasing number of geometric error parameters from probe data. — [Duet3D Delta calibration docs](https://docs.duet3d.com/User_manual/Tuning/Delta_calibration), [RepRap wiki: Configuring/calibrating a delta printer using dc42 RepRapFirmware fork](https://reprap.org/wiki/Configuring_and_calibrating_a_delta_printer_using_the_dc42_fork_of_RepRapFirmware)
- **Klipper's `Delta_Calibrate.md`**: the calibrated parameters are tower endstop positions, tower angles, delta radius, and delta arm (rod) lengths. Klipper supports both manual "paper test" probing at each point and automatic Z-probe calibration (the docs note that some probes can introduce >25-micron bias). Basic calibration uses 7 probe points to solve for new parameter values; an enhanced mode adds a physically-measured test-object distance to refine parameters further. The docs explicitly note that small arm-length errors cause effector tilt that skews measurements, and that the algorithm favors parameter values that produce better real-world accuracy over theoretically "correct" values. — [Klipper Delta_Calibrate.md](https://raw.githubusercontent.com/Klipper3d/klipper/master/docs/Delta_Calibrate.md)
- An independent **least-squares delta calibration calculator** (escher3d "Delta printer least-squares calibration calculator") exists as a web tool that takes probe-point data and solves for delta geometry parameters via least squares — an example of extracting the math out of the firmware into a standalone reusable calibration tool. — [escher3d delta calibration wizard](https://escher3d.com/pages/wizards/wizarddelta.php) (page not fetched in full; listed as a search result, not independently verified beyond title/description)
- The RepRap wiki also has a dedicated **"Delta geometry"** page describing the parameters (rod length, radius, tower angles, endstop offsets) that define delta kinematics. — [RepRap wiki: Delta geometry](https://reprap.org/wiki/Delta_geometry) (fetch blocked by network egress proxy in this session; only the URL/title is confirmed, content not verified firsthand)

### Inferences
- None of these firmwares calibrate *servo PWM-to-angle* relationships directly — they calibrate stepper-driven geometric parameters using an external ground-truth (a touch probe or manual paper-test) — but the same architecture (define a small parameter vector describing systematic error, collect measurements at several points spanning the workspace, and solve for the parameter vector that minimizes position error, typically via least squares) is a solid template for a hobbyist wanting to jointly calibrate 3 servo angle offsets/scales on a delta robot using measured end-effector positions (e.g., from a camera or touch probe) rather than calibrating each servo's PWM curve in isolation.
- The distinction between "3/4/6/8-factor" calibration models in RepRapFirmware is a useful practical illustration of how to scale calibration complexity (start with just offsets, add scale/radius, then add per-actuator angular corrections) — directly analogous to a servo calibration approach that starts with per-servo offset, then adds scale, then adds cross-axis/geometric corrections.

### Gaps
- Could not find any firmware (delta or otherwise) that calibrates *servo* PWM pulse-width-to-angle curves as part of its auto-calibration routine — these are all stepper/probe based. No servo-driven delta 3D-printer-style firmware with an analogous auto-cal routine was found.
- Full content of the RepRap "Delta geometry" wiki page and the escher3d least-squares calculator's internal math could not be retrieved (network egress to reprap.org and escher3d.com-adjacent verification was blocked); only search-result summaries are available for the wiki page, and only the tool's existence/purpose is confirmed for escher3d.

## Key Question 2: Are there Arduino libraries/sketches (beyond Servo.h) implementing calibrated angle-to-pulse or pulse-to-angle conversion with per-servo calibration constants (offset, scale, direction)?

### Takeaway
Yes — several purpose-built libraries and sketches exist beyond the stock `Servo.h`, ranging from a simple "pass `min`/`max` pulse width to `attach()`" pattern, to a dedicated `ServoProfile` class that fits a per-servo second-order curve from 3 measured reference points, to a full closed-loop encoder-based calibration tool (`Servo-Calibrator`) that builds a 20-point per-servo lookup table and exports it as a ready-to-compile header.

### Cited Findings
- The standard Arduino `Servo.h` linearly maps `servo.write(angle)` over 0–180° onto a pulse-width range (default ~544–2400 µs, i.e. `pulse_us = min_us + (angle/180.0) * (max_us - min_us)`); calibration is done by calling `attach(pin, min, max)` with per-servo-measured min/max pulse widths. — [Arduino Forum: converting servo sketches angle↔pulsewidth](https://forum.arduino.cc/t/is-there-a-simple-way-to-convert-servo-sketches-from-angle-to-position-pulsewidth-and-viseversa/934128) (per WebSearch synthesis)
- **`solosodium/Arduino-PCA9685`** (GitHub) implements a `ServoProfile` class (`servoprofile.h`/`servoprofile.cpp`) that is constructed with 3 reference pulse widths at 0°, 90°, and 180° (e.g. `ServoProfile servo(0.6, 1.5, 2.4);`, values in ms) and fits a **second-order (quadratic) curve** through those 3 calibration points; its `computePulseWidth(angle)` method then converts a desired turning angle to the correct pulse width using the fitted curve. The repo also ships an interactive calibration sketch (`sketch.ino`) with serial commands `set;<reference degree>;<pulse width in ms>` to store calibration points, `test;<turning angle>` to validate the profile, and `pulse;<pulse width>` for direct manual pulse testing — i.e., a full manual per-servo calibration workflow with no extra hardware needed beyond a way to read the arm angle by eye/protractor. — [github.com/solosodium/Arduino-PCA9685](https://github.com/solosodium/Arduino-PCA9685)
- **`vishwam-aggarwal/Servo-Calibrator`** (GitHub): a browser-based (Web Serial API) servo range-finder and calibration wizard that uses an **AS5600 magnetic encoder** on the servo output shaft as ground truth, rather than trusting the commanded angle. Instead of a single linear or quadratic formula, it builds a **20-point directional lookup table** (`CalPoint` array of `{pulseUs, angleCentideg}` pairs) via a coarse-then-fine bidirectional sweep, self-calibrating step rates and detecting mechanical end-stops by watching for stalled/reversed encoder response; it sweeps the full range twice (once per direction) and averages results, then normalizes the table to `[0, maxAngleDeg]`. Reported error reduction: ~3.13° (naive) down to ~0.19° (table-based). The firmware (`ServoCalibrator_Companion.ino`) runs a fixed 50 Hz state machine using an `AS5600EncoderDriver` and a `TrapezoidalProfile` motion planner; the companion web app (`website/app.html`) shows live position/velocity/error charts and can toggle linear-vs-table interpolation, then **exports a `.h` file with a populated `CalPoint` array** sized to match the "Universal-Motor-Interface" project's data structure, for direct reuse with that project's `RCServoMotorDriver`/`PCA9685MotorDriver` classes (the export is characterization data only — direction and mounting-offset handling are left to the calling application). Depends on RobTillaart's AS5600 library plus companion "Universal-Encoder-Interface", "Universal-Trajectory-Interface", and "Universal-Device-Interface" libraries by the same author family. — [github.com/vishwam-aggarwal/Servo-Calibrator](https://github.com/vishwam-aggarwal/Servo-Calibrator)
- A basic Arduino Gist (`jestin/118ea8fec7dfeed91767`, "Sample Arduino code that can be used to calibrate a servo") turned out on inspection to be a minimal serial-driven servo test sketch (reads an integer from Serial, calls `myservo1.write(n1)`), with **no actual calibration math, offset/scale constants, or angle-to-pulse mapping logic** — useful only as a manual jog/probe tool for *finding* calibration points by hand, not as a calibration algorithm itself. — [gist.github.com/jestin/118ea8fec7dfeed91767](https://gist.github.com/jestin/118ea8fec7dfeed91767) (verified directly by fetch)
- Multiple step-by-step calibration walkthroughs with Arduino code exist on Instructables ("Calibrating Hobby Servo Motors Using Arduino", "Calibrating Servos for Bracket/robot Arm", "Servo Motor Positioning-calibration How to Tutorial") and Hackster.io ("Calibrating My Servos" by Jeremy Lindsay); these were identified by search but their full code content could not be fetched in this session (see Gaps). — [instructables.com/Calibrating-Hobby-Servo-Motors-Using-Arduino](https://www.instructables.com/Calibrating-Hobby-Servo-Motors-Using-Arduino/), [instructables.com/Calibrating-Servos-for-Bracketrobot-Arm](https://www.instructables.com/Calibrating-Servos-for-Bracketrobot-Arm/), [instructables.com/Servo-Motor-Positioning-calibration-How-to-Tutoria](https://www.instructables.com/Servo-Motor-Positioning-calibration-How-to-Tutoria/), [hackster.io/jeremy-lindsay/calibrating-my-servos-fa27ce](https://www.hackster.io/jeremy-lindsay/calibrating-my-servos-fa27ce)
- Adafruit's "Analog Feedback Servos" guide includes a "Calibrating the Feedback" section describing how to calibrate the analog position-feedback wire against known commanded angles for feedback-capable servos (e.g. Adafruit's continuous/positional feedback servos) — a distinct but related calibration axis (feedback-signal-to-angle, not just command-to-angle). — [learn.adafruit.com/analog-feedback-servos/calibrating-the-feedback](https://learn.adafruit.com/analog-feedback-servos/calibrating-the-feedback) (identified via search, content not independently fetched)

### Inferences
- **Directly reusable**: `Servo-Calibrator` (full closed-loop, encoder-verified, exports a ready-to-include `.h` calibration table) and `Arduino-PCA9685`'s `ServoProfile` class (lightweight, no extra hardware, 3-point quadratic fit) are the two strongest directly-reusable code assets found — they span the two main calibration strategies (empirical lookup table vs. parametric curve fit) that a delta-robot builder would choose between depending on whether they have an angle sensor available.
- The Gist and most Instructables/Hackster tutorials are **conceptually instructive at best** (manual procedure: sweep pulse width, note visually/mechanically where limits or center are, hardcode `min`/`max` into `attach()`) rather than directly reusable calibration code — several of these could not be fully verified in this session and should be treated cautiously.

## Key Question 3: MATLAB/Python/ROS packages or example scripts for fitting a servo calibration curve from measured (pulse_width, angle) data?

### Takeaway
No dedicated, packaged MATLAB/PyPI/ROS "servo calibration curve-fitting" library was found; instead, the consistent pattern across every source is a short custom script using `polyfit` (MATLAB/NumPy) for a linear fit or `scipy.optimize.curve_fit` for a more general nonlinear fit, applied to manually or encoder-collected (pulse_width, angle) data pairs — and for joint-level (not raw-PWM) calibration, ROS has real per-joint offset/scale parameters in Dynamixel hardware-interface packages.

### Cited Findings
- A Swarthmore College robotics lab exercise ("E5 Matlab 3: coding the servos") describes a **`ServoCalibrate.m`** MATLAB script that prompts the user for a pulse width (µs), sends it to a servo channel, and has the user record the resulting angle; after collecting several (pulse width, angle) pairs, the relationship is plotted and MATLAB's **`polyfit`** command is used to compute the slope and intercept of the best-fit line, which is then used to compute the pulse width needed for any desired angle. — [archive.swarthmore.edu E5Matlab3](https://archive.swarthmore.edu/www1/NatSci/ceverba1/Class/e5/LabServo/E5Matlab3.html) (identified via WebSearch synthesis; direct fetch of the page was blocked by the network egress proxy in this session, so exact script contents are not independently verified)
- General SciPy guidance confirms `scipy.optimize.curve_fit(f, xdata, ydata)` performs nonlinear least-squares fitting of a user-supplied model function `f` to (x, y) data — directly applicable to fitting either a straight line or a more general (e.g. quadratic/sigmoid) pulse-width-vs-angle model when a servo's response isn't perfectly linear. — [SciPy curve_fit reference docs](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.curve_fit.html)
- A DIY quadruped-robot Hackaday.io project log ("Calibrating the servos," part of "DIY Hobby Servos Quadruped Robot") reportedly converts servo angles to pulse widths using a calibrated linear relationship (scale factor and offset) per search-result synthesis, but the page itself (hackaday.io) was blocked by the network egress proxy in this session and could not be independently fetched/verified. — [hackaday.io/project/171456-diy-hobby-servos-quadruped-robot/log/181663-calibrating-the-servos](https://hackaday.io/project/171456-diy-hobby-servos-quadruped-robot/log/181663-calibrating-the-servos) (unverified — see Gaps)
- On the ROS side, calibration is handled at the **joint** level rather than raw PWM: **`dynamixel_hardware`** (dynamixel-community, ros2_control hardware interface for ROBOTIS Dynamixel) exposes per-joint `gear_ratio`, `offset`, and `torque_constant` parameters so that ros2_control commands/reads joint radians and Nm while the interface converts to/from motor revolutions and mA internally. — [github.com/dynamixel-community/dynamixel_hardware](https://github.com/dynamixel-community/dynamixel_hardware)
- **`resibots/dynamixel_control_hw`** (ROS 1, hardware interface for ros_control with Dynamixel actuators) has a configuration-file `offset` parameter that is a correction value applied per joint's actuator, directly analogous to a per-servo trim/offset constant. — [github.com/resibots/dynamixel_control_hw](https://github.com/resibots/dynamixel_control_hw)
- **DYNAMIXEL Workbench** and the older **`dynamixel_controllers`** ROS package both provide the standard ROS-ecosystem tooling for talking to Dynamixel servos with configurable per-joint controller parameters, though the search results did not surface calibration-curve-fitting code specifically (mostly configuration/YAML-driven offset handling). — [emanual.robotis.com dynamixel_workbench](https://emanual.robotis.com/docs/en/software/dynamixel/dynamixel_workbench/), [wiki.ros.org dynamixel_controllers](http://wiki.ros.org/dynamixel_controllers/Tutorials/Creating%20a%20joint%20torque%20controller)

### Inferences
- There is a real gap between hobby-RC-servo PWM calibration (which is almost always solved with a short ad hoc `polyfit`/`curve_fit` script against manually recorded data, never packaged as a reusable library) and smart-servo (Dynamixel) calibration (which is built into the ROS hardware-interface config as an `offset`/`gear_ratio` parameter because Dynamixels report their own absolute position). A delta-robot builder using RC servos should expect to write their own small polyfit/curve_fit script rather than find a polished package; if using Dynamixels instead of RC servos, the ROS `dynamixel_hardware`/`dynamixel_control_hw` offset mechanism is directly reusable.
- Given the AS5600-based `Servo-Calibrator` project's finding that a 20-point lookup table cuts error 2–6× versus a single linear formula, a pure `polyfit`-degree-1 fit (as in the MATLAB E5 example) is likely insufficient for high-precision delta-robot work; a higher-order fit (`polyfit` degree 2–3) or full lookup table is the more defensible approach for final calibration, matching what `Arduino-PCA9685`'s quadratic `ServoProfile` and `Servo-Calibrator`'s lookup table already do in firmware.

### Gaps
- No MATLAB File Exchange submission specifically titled/dedicated to "servo PWM calibration" was found; File Exchange results returned were generic PWM-generation/Simulink blocksets (sinusoidal PWM, space-vector PWM, "Servo System Blockset"), not curve-fitting-for-calibration tools. This appears to be a genuine gap — MATLAB users doing this seem to write their own short polyfit script (as in the Swarthmore example) rather than using a published package.
- No PyPI package specifically for "servo calibration curve fitting" was found in this research pass; only generic `scipy.optimize.curve_fit` usage guidance. A more targeted PyPI-specific search (e.g. via pypi.org search directly) was not performed due to tool-call budget and could close this gap in a follow-up pass.

## Key Question 5: Do industrial robot calibration methodologies (e.g. DH parameter calibration) have simplified hobbyist analogs?

### Takeaway
Yes conceptually: industrial DH-parameter kinematic calibration (measure real end-effector poses, solve for corrected DH parameters that minimize position error, typically via least-squares/optimization) has a documented simplified hobbyist form using a calibration board/fixture and an optimization solve, and the same least-squares-over-measured-points philosophy underlies the delta-robot firmware calibration routines in Key Question 1 — but no specific ready-made hobbyist code repository implementing DH calibration for a servo arm was found in this pass.

### Cited Findings
- Industrial robots ship from the factory with a per-unit calibration file recording deviations of the physical arm's actual DH parameters from the nominal/design values, measured and stored before the robot leaves the factory. — [Universal Robots ROS2 Driver: Calibration correction algorithm docs](https://docs.universal-robots.com/Universal_Robots_ROS2_Documentation/doc/ur_robot_driver/ur_calibration/doc/algorithm.html) (per WebSearch synthesis)
- A described hobbyist-adjacent approach: use a **calibration board** where the end-effector samples multiple known points to establish the relationship between the world coordinate frame and the robot's own coordinate frame, and solve for the DH parameters via optimization of the resulting error equations — i.e., a simplified, single-fixture version of full kinematic calibration. — (per WebSearch synthesis; original source article not individually identified/fetched, so treat as a general-technique summary rather than one attributable single project)
- A 2025 arXiv paper, "A novel step-by-step procedure for the kinematic calibration of robots using a single draw-wire encoder," describes estimating DH parameters one at a time using only 1D distance measurements from a single draw-wire encoder — an explicitly low-cost-hardware approach to kinematic calibration that a hobbyist could plausibly replicate with a cheap wire-encoder/string-potentiometer instead of expensive metrology equipment. — [arxiv.org/html/2502.14983v1](https://arxiv.org/html/2502.14983v1)
- Duet3D's documentation includes a page on configuring **"Robot Denavit-Hartenberg (DH) parameters"** for non-delta robot kinematics support in RepRapFirmware, showing that the RepRap/3D-printer-firmware ecosystem has already extended beyond delta-specific calibration into general DH-parameter-based robot configuration. — [docs.duet3d.com: Configuring Robot DH parameters](https://docs.duet3d.com/User_manual/Machine_configuration/Configuring_Robot_DH_parameters)
- For hobbyists wanting to experiment with DH-parameter kinematics/calibration in software, commonly recommended free tools are ROS + RViz, Peter Corke's Robotics Toolbox for Python, and the MATLAB Robotics System Toolbox. — (per WebSearch synthesis of multiple general how-to articles, e.g. [zbotic.in DH parameters guide](https://zbotic.in/robot-arm-forward-kinematics-dh-parameters-equations-guide/), [fusybots.com DH parameters guide](https://www.fusybots.com/post/how-to-calculate-dh-parameters-for-robotic-arms-a-beginner-s-guide))
- Delta-robot-specific academic kinematic calibration work exists and quantifies achievable improvement: two calibration models are described in the literature — one ("model 54") accounting for deviations of all mechanical parts except spherical joints, and another ("model 24") considering only end-effector position (not orientation) deviations — with reported absolute accuracy improving from ~1.4 mm to ~0.1–0.13 mm after calibration. — [Cambridge Core: Kinematic calibration of the parallel Delta robot](https://www.cambridge.org/core/journals/robotica/article/abs/kinematic-calibration-of-the-parallel-delta-robot/A72E015D75BFF1D8EBE2A503B7441405), [ResearchGate PDF of same](https://www.researchgate.net/publication/232019465_Kinematic_calibration_of_the_parallel_Delta_robot)
- A related paper, "Kinematic sensitivity, parameter identification and calibration of a non-fully symmetric parallel Delta robot," addresses calibration specifically for Delta robots whose three arms are not perfectly symmetric — relevant to a hobbyist-built delta robot where the three arms are very unlikely to be perfectly identical/symmetric. — [ScienceDirect: Kinematic sensitivity...non-fully symmetric parallel Delta robot](https://www.sciencedirect.com/science/article/abs/pii/S0094114X21000690)

### Inferences
- No hobbyist GitHub repo was found that implements full DH-parameter (or delta-specific "model 24/54") kinematic calibration in accessible code (e.g., a Python/MATLAB script that takes measured end-effector positions and outputs corrected kinematic parameters for a servo-driven arm). This is a genuine gap in the hobbyist ecosystem: the *industrial/academic* methodology is well documented (see the Cambridge Core / ScienceDirect papers above), and the *delta-3D-printer-firmware* calibration methodology is well documented and open-source (Marlin/Klipper/RepRapFirmware, see Key Question 1), but a bridge repo applying the delta-specific calibration math to a *servo*-actuated hobby delta robot (rather than stepper+probe) was not located. This is a concrete opportunity: the Marlin/Klipper delta calibration source code (which is open and readable, e.g. Klipper's `delta_calibrate.py`-equivalent by search result, and Marlin's G33 implementation) could plausibly be adapted/ported by a capstone-style project to a servo-driven delta robot, since the underlying geometric model (3 arms, tower-angle offsets, effective radius, rod length) is identical regardless of actuator type — only the "endstop offset per tower" calibration term would be replaced conceptually by a per-servo PWM offset/scale term.
- Peter Corke's Robotics Toolbox for Python (mentioned repeatedly as the standard free hobbyist/academic DH-parameter tool) is worth the user's own follow-up look, since it likely has built-in utilities for defining a DH-parameter robot model and could be paired with a custom least-squares calibration routine (not itself a calibration package, but the modeling substrate one would build a calibration script on top of).
